= Introduction

{product} scaffolds a repository of Architecture Decision Records and Solution
Designs, then owns every rule that governs it. Repositories it creates carry no
scripts of their own: the binary is the single source of truth for the rules, so
they cannot drift between the repositories that share them.

The full design — why the schema is shaped this way, what is deliberately not
built, and the phased roadmap — is recorded in `DESIGN.md` at the root of the
repository. This manual documents how to operate what has actually been built.

== Install

[source,sh]
----
brew install codcod/tap/jerry
----

Or, on any machine with a Go toolchain:

[source,sh]
----
go install github.com/codcod/jerry/cmd/jerry@latest
----

== Create a repository

[source,sh]
----
mkdir architecture-docs && cd architecture-docs
git init
jerry init --forge github     # or --forge gitlab
jerry hooks install
----

`init` writes templates, an example ADR, CODEOWNERS, CI for the chosen forge,
`jerry.yaml`, and a generated index. It is idempotent: existing files are
reported and left alone unless `--force` is given. Use `--dry-run` first to see
the list.

The emitted CI pins the version of {product} that wrote it, so a repository
keeps being checked against the rules it was created with until somebody bumps
the pin deliberately.

== Write a decision

[source,sh]
----
jerry new adr "Use event sourcing for the ledger" --team payments
----

This allocates the next free four-digit id in that folder, slugs the title into
a filename, stamps today's date and fills `deciders` from your git identity. The
body arrives as prompts written in HTML comments, which do not count as content
— a document created and never filled in still fails validation.

For a decision that binds more than one team:

[source,sh]
----
jerry new adr "Standardise on OpenTelemetry" --cross-cutting --teams payments,platform
----

Solution designs work the same way, with `jerry new sd`. They have no sequential
id: the date is the identifier, so the filename is `YYYY-MM-<slug>.md` and its
prefix must agree with the frontmatter date.

== Check it

[source,sh]
----
jerry validate
jerry index --check
----

`validate` reports every problem it finds rather than stopping at the first, and
exits non-zero when at least one is an error. Warnings — an ADR left `Proposed`
for more than ninety days — are printed but never fail: that judgement needs a
human, and failing a pipeline on the calendar only teaches people to falsify
dates.

For CI that annotates the diff instead of a log nobody opens:

[source,sh]
----
jerry validate --format sarif > jerry.sarif
----

`--format` also accepts `text`, `json` and `junit`.

`validate` also flags an unfilled template placeholder anywhere in the document, except inside a
fenced code block — quoting a template is not the same as forgetting to fill one in. A document
that legitimately discusses a placeholder phrase — documenting the `ADR-NNNN` id convention, say
— opts out of the whole check for that document with an inline `<!-- jerry:allow placeholder
-->` marker.

== Change a status

[source,sh]
----
jerry status payments/ADR-0007 accepted
----

Transitions are checked. `Rejected` is a real outcome and worth recording: it is
what stops the same proposal returning every year. `Superseded` is deliberately
unreachable here, because it needs a successor to point at:

[source,sh]
----
jerry supersede payments/ADR-0007 --with "Use CockroachDB for the ledger"
----

That one command creates the successor, sets `status: Superseded` and
`superseded_by:` on the predecessor, writes the reverse `supersedes:` pointer,
and adds the note under Consequences. Doing it by hand is how one half of the
link ends up missing.

== References between decisions

IDs are unique per folder, not globally. A bare `ADR-0007` therefore means "in
this document's own folder"; anything else must name its scope.

[cols="1,2"]
|===
| Reference | Means

| `ADR-0007`
| ADR-0007 in the same folder

| `payments/ADR-0007`
| ADR-0007 in `teams/payments/adr/`

| `cross-cutting/ADR-0003`
| ADR-0003 in `cross-cutting/adr/`
|===

Every `superseded_by`, `supersedes` and `related_adrs` entry is resolved against
the corpus.

`applies_to` entries are validated as paths: an empty or whitespace-only entry, an
absolute path, or a `..`-traversal is an error. Matching those paths against a
repository is a gitignore-style dialect — directory prefixes and glob segments,
most-specific-pattern-wins when several decisions match one path — described
below under "Resolve a path to its governing decisions". Any frontmatter key
{product} does not recognise is reported as a warning rather than silently
preserved — see the note on `fmt` below about what "preserved" still means.

`schema_version` defaults to `1` and stays optional. `validate` warns — never
errors — when a document's `schema_version` is newer than this binary knows,
and still checks it with the newest rules available: an old {product} must
never turn a repository red for being newer than itself, since upgrading
{product} is not meant to be a prerequisite for merging anything.

== Resolve a path to its governing decisions

[source,sh]
----
jerry related --paths teams/payments/src/ledger.go --paths docs/readme.md
----

Resolves each `--paths` entry against every decision's `applies_to`, offline,
from the terminal — no network, no forge lookup. In the default text format, a
queried path with no governing decision renders no line: silence is the
expected shape for "nothing governs this," not an error. `related` is a
query, not a gate, so it exits non-zero only on bad input (an empty
`--paths`, a corpus that fails to load), never because nothing matched.

`--format json` emits a versioned envelope (`jerry.related/1`) instead, one
entry per queried path, decisions ordered most-specific-pattern-first — the
same order `--format text` renders, never re-ranked or collapsed to a single
winner.

== Post governing decisions to a merge request

[source,sh]
----
jerry comment            # run in CI, on a merge request
jerry comment --dry-run  # preview the comment body, post nothing
----

Runs the same query as `related` over the merge request's changed files
(`--base`, default `origin/main`) and posts — or updates, never duplicates —
a comment listing the decisions that govern them. Nothing is posted, and
nothing is logged, when no changed file matches any decision: silence is the
expected shape, the same as `related`'s.

Meant to run as a CI step, using the forge's own `GITHUB_TOKEN`. A missing
token is a silent no-op, the same as no match: nothing printed, exit 0. Any
other failure — an insufficiently-scoped token, a network error, a non-2xx
response — logs one line to stderr but still exits 0 and posts nothing. A
docs tool must never be the reason a merge request cannot merge.

Every successful post appends one line to `jerry-adoption.jsonl` at the repo
root (override with `--adoption-log`) — `{"repo", "pr", "decisions",
"timestamp"}` — so whether the comment is actually read is answerable from
the first post onward, not only once a separate reporting tool exists. This
is a new file that will appear in a repository's root the first time
`comment` successfully posts; commit it like any other generated artifact.

== Formatting

[source,sh]
----
jerry fmt          # canonicalise
jerry fmt --check  # list files that need it, exit non-zero
----

`fmt` normalises frontmatter key order and trailing whitespace, and preserves
keys {product} has never heard of in their authored order. It never reflows
prose: deciding what is a paragraph and what is a list, table or fenced block is
exactly where a markdown formatter corrupts authored text.

== Editor support

[source,sh]
----
jerry schema --kind adr > adr.schema.json
----

Point any YAML language server at the result for frontmatter completion and
inline validation. The published `schema_version` constraint is a floor
(`minimum`), not an equality, so a document written by a newer {product}
still validates against an older binary's schema instead of being rejected
outright.

== Configuration

`jerry.yaml` is optional; every key falls back to the default `jerry init`
writes. It is located by walking upward from the working directory, the way git
and cargo find their manifests, so {product} works from anywhere inside the
repository.

[source,yaml]
----
adr-dir: adr
solution-design-dir: solution-designs
skip-dirs: [templates, index, .git, node_modules, dist]
index-path: index/index.md
required-adr-sections: ["## Context", "## Decision", "## Consequences"]
required-sd-sections: ["## Problem Statement", "## Proposed Design", "## Risks & Trade-offs"]
proposed-stale-days: 90
----

== Global flags

`-c, --config` names a `jerry.yaml` explicitly. `--json` emits machine-readable
output where a command has one. `-q, --quiet` suppresses progress but never
errors. Every command that writes accepts `--dry-run`.
